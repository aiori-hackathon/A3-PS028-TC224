## 1. Executive Summary & Purpose

The Happy Eyeballs (RFC 8305) Measurement Lab evaluates dual-stack IPv4/IPv6 racing and fallback behaviors under controlled synthetic impairments. Rigorous scientific analysis requires unambiguous, mathematically grounded distinctions between high-level experiment execution lifecycles, transport-layer socket state transitions, packet-level network events, and out-of-band diagnostic telemetry.

This document establishes the binding normative definitions for all terms, identifiers, states, and metric concepts used across the testbed runner (`lab/run_trial.py`), campaign manager (`lab/run_campaign.py`), analysis engine (`lab/analyze.py`), and evidence exporter (`lab/export_campaign_evidence.py`).

## 2. Four-Tier Measurement Hierarchy

To eliminate category conflation, measurement operations in the PS-028 testbed are structured into four strictly nested, non-overlapping architectural tiers:

```
+-------------------------------------------------------------------------------+
| Tier 1: Matrix Slot (slot_id)                                                 |
| Planned permutation of (scenario_id, browser, repetition_index)               |
| E.g.: slot-0002-S0-firefox-rep01 (Total slots: 280)                           |
+-------------------------------------------------------------------------------+
        |
        | 1:N (1 in healthy executions, >1 if cleanup/preflight fault triggers rerun)
        v
+-------------------------------------------------------------------------------+
| Tier 2: Harness Attempt (attempt_id, trial_id)                                |
| End-to-end execution of a trial slot by the testbed runner                   |
| Total attempts: 282 (280 VALID_LIVE + 2 preserved CLEANUP_FAILURE)            |
+-------------------------------------------------------------------------------+
        |
        | 1:N (Multiple concurrent/sequential socket attempts during racing)
        v
+-------------------------------------------------------------------------------+
| Tier 3: Network Connection Attempt (connection_attempt)                       |
| Single TCP SYN segment launched on the wire towards target service 5-tuple    |
| Total across historical campaign: 765 connection attempts                     |
+-------------------------------------------------------------------------------+
        |
        | 1:1 (Each unique 4-tuple TCP conversation is dissected by TShark)
        v
+-------------------------------------------------------------------------------+
| Tier 4: TCP Stream (tcp.stream)                                               |
| Wireshark/TShark transport-layer session index (0, 1, 2, ...)                 |
| Transport container; NOT an application transaction                           |
+-------------------------------------------------------------------------------+

[Orthogonal Out-of-Band Track]
+-------------------------------------------------------------------------------+
| Diagnostic Probe (probe)                                                      |
| Standalone network packet/measurement launched by diagnostic utilities        |
| (e.g. privileged_helper.py measure-s5, ping, preflight checks)                |
| NEVER generated by the browser; NEVER conflated with browser connection racing|
+-------------------------------------------------------------------------------+
```

## 4. Rigorous Normative Definitions

### 4.1 Attempt (`attempt` / `harness_attempt`)
- **Definition**: An end-to-end discrete invocation of a single test matrix slot by the testbed orchestration harness (`lab/run_trial.py`).
- **Lifecycle**:
  1. Preflight baseline verification (ensures namespaces `ps028-cl`, `ps028-rt`, `ps028-sv` are healthy and clean).
  2. Impairment configuration application (`tc netem` delay/loss, `nftables` drop/reset rules, DNS server delay profile).
  3. Packet capture daemon initialization (`tcpdump` on `ps028-cl-rt`).
  4. Browser process execution with isolated user-data-dir and active navigation to `http://<trial-hostname>/`.
  5. Post-navigation wait, browser process termination, and capture termination.
  6. Post-trial impairment teardown and baseline restoration.
  7. Packet capture dissection and JSON artifact emission.
- **Invariants**:
  - Every attempt produces a dedicated directory `trials/<trial_id>/`.
  - If preflight or cleanup encounters an unrecoverable failure (e.g. broken pipe or missing privileges), the attempt is recorded as `CLEANUP_FAILURE` and saved in `failed_attempt_record.json`. The matrix slot re-executes with a fresh attempt (`attempt_number: 2`).
  - Total attempts in the authoritative October 29 campaign: **282** (280 valid live trials + 2 preserved cleanup failures).

### 4.2 Connection Attempt (`connection_attempt`)
- **Definition**: A packet-level network operation initiated by the client operating system or browser network stack consisting of an initial TCP SYN segment with a specific 5-tuple transmitted toward the target HTTP service.
- **5-Tuple Composite**:
  $$\text{5-Tuple} = (\text{family}, \text{client\_ip}, \text{client\_port}, \text{server\_ip}, \text{server\_port})$$
- **Invariants**:
  - Governed by RFC 9293 §3.5 and RFC 8305 §5.
  - A single harness attempt frequently generates multiple connection attempts:
    - In S0/S3 (dual-stack immediate IPv6 win): 1 primary IPv6 connection attempt, plus potential ancillary/speculative connections.
    - In S1/S2/S4/S5 (Happy Eyeballs fallback): 1 initial IPv6 connection attempt followed by 1 or more IPv4 fallback connection attempts.
    - In S5 (50% stochastic loss): multiple connection attempts across both families due to SYN retransmissions and parallel racing sockets (up to 5 streams observed per trial).
  - **Retransmission Rule**: A retransmitted SYN on the same 5-tuple is NOT a new connection attempt; it is a retransmission of the existing attempt and must increment `retransmitted_syn_count` without advancing the initial `syn_time`.

### 4.3 Probe (`probe` / `diagnostic measurement`)
- **Definition**: An isolated, synthetic, out-of-band network transmission executed by diagnostic or infrastructure management tools specifically to inspect, measure, or validate underlying network state.
- **Distinguishing Criteria**:
  - Probes originate from auxiliary utilities (e.g., `lab/privileged_helper.py measure-s5`, ping, curl, netcat), NEVER from the browser binary.
  - Probes execute outside the experimental trial lifecycle (e.g., during preflight verification or independent netem calibration sweeps).
  - Probes emit structured JSONL or stdout metrics and are strictly quarantined from experimental PCAP traces to prevent skewing browser behavioral distributions.

### 4.4 TCP Stream (`tcp.stream`)
- **Definition**: An integer session identifier assigned by Wireshark/TShark's TCP dissector to group all packets belonging to a bidirectional 4-tuple TCP conversation (`client_ip:client_port <-> server_ip:server_port`) over the entire capture duration.
- **Disambiguation from Application Operations**:
  - A `tcp.stream` is purely a transport-layer encapsulation.
  - A `tcp.stream` MUST NEVER be equated to an HTTP request, navigation, or Happy Eyeballs trial.
  - In modern browsers, a single page navigation (`GET /`) may open speculative preconnect streams, separate streams for subresources or icons (`GET /favicon.ico`), or abandoned streams that were initialized during racing but never transmitted HTTP data.
  - The analysis engine must correlate HTTP methods and response codes (`http.request.method == "GET"`) to identify the exact stream serving the primary navigation document (`is_primary = True`).

## 5. Flow Classification & Role Taxonomy

Every TCP stream observed in a trial capture is assigned exactly one flow role:

```
               [All Observed TCP Streams in Trial]
                               |
       +-----------------------+-----------------------+
       |                                               |
[Handshake Completed?]                        [Handshake Failed / Timed Out]
       |                                               |
       +--------------------+                          +--------------------+
       |                    |                          |                    |
[HTTP GET / Carried?] [No Main GET /]             [SYN Discarded]     [SYN Reset]
       |                    |                          |                    |
       v                    v                          v                    v
PRIMARY_FLOW         ANCILLARY_FLOW             NO_SYNACK_TIMEOUT        RESET
(is_primary=True)    (is_primary=False)         (is_primary=False)  (is_primary=False)
```

1. **`PRIMARY` (`ESTABLISHED_PRIMARY`)**:
   - The unique TCP connection that successfully completes the three-way handshake (`SYN` $\to$ `SYN/ACK` $\to$ `final ACK`) and transmits the primary HTTP `GET /` (or `/index.html`) request, receiving the terminal `200 OK` document.
   - Strictly exactly one primary stream per successful trial.
2. **`ANCILLARY` (`ESTABLISHED_ANCILLARY`)**:
   - A secondary TCP connection that successfully completes the three-way handshake but serves secondary browser traffic (e.g., `/favicon.ico`, warm socket pool, or speculative preconnect).
3. **`SPECULATIVE` / `ABANDONED`**:
   - A TCP connection initiated during the Happy Eyeballs race that received a `SYN/ACK`, but was abandoned by the client (no final ACK, or immediate RST sent) because an alternate connection established first and won the race.
4. **`RESET`**:
   - A TCP connection whose SYN segment was actively rejected with a TCP RST by the server or router (e.g. Scenario S2).
5. **`NO_SYNACK_TIMEOUT`**:
   - A TCP connection whose SYN segment was transmitted on the wire, but no response was ever received due to blackholing or packet drop (e.g. Scenario S1, S5).

## 6. Mathematical Metric Definitions

### 6.1 `t_connect_ms` (Primary Handshake Latency)
- **Standard**: RFC 9293 §3.5 (Handshake Completion), Decision 1
- **Definition**: Elapsed time from initial client SYN on the primary stream to matching client final ACK:
  $$t_{\text{connect}} = \left( t_{\text{final\_ack, primary}} - t_{\text{initial\_syn, primary}} \right) \times 1000$$
- **Invariance**: Retransmitted SYNs do not advance $t_{\text{initial\_syn}}$.

### 6.2 `t_setup_total_ms` (Fallback Total Setup Time)
- **Standard**: Amendment A3, Decision 1
- **Definition**: Elapsed time from the client's first SYN of any address family in the trial to the final ACK of the primary stream:
  $$t_{\text{setup\_total}} = \left( t_{\text{final\_ack, primary}} - \min_{f \in \{\text{IPv4}, \text{IPv6}\}} \left( t_{\text{first\_syn, } f} \right) \right) \times 1000$$
- **Significance**: In fallback scenarios, captures the total stall experienced by the client, including the Connection Attempt Delay (CAD).

### 6.3 `syn_to_synack_ms` (Diagnostic Path RTT Proxy)
- **Standard**: Rule R3, Finding C1-03
- **Definition**: Historical metric measuring elapsed time from initial SYN to server SYN/ACK on the primary stream:
  $$t_{\text{syn\_to\_synack}} = \left( t_{\text{synack, primary}} - t_{\text{initial\_syn, primary}} \right) \times 1000$$

### 6.4 `cad_ms` (Connection Attempt Delay)
- **Standard**: RFC 8305 §5
- **Definition**: Time elapsed between the initial SYN of the preferred address family (IPv6) and the initial SYN of the fallback address family (IPv4):
  $$\text{CAD} = \left( t_{\text{first\_syn, IPv4}} - t_{\text{first\_syn, IPv6}} \right) \times 1000$$
- **Validity Rule**: Null with reason `INVALID_FAMILY_CHRONOLOGY` if IPv4 is attempted first.

## 7. Fallback Classification & Validity Enums

### 7.1 Fallback Classification Enum (`FallbackClassification`)
Every trial receives exactly one classification from the canonical shared enum:

- **`DIRECT_IPV6`**: IPv6 primary stream established and served `GET /`; no IPv4 SYN sent, or IPv4 SYN sent after IPv6 established.
- **`DIRECT_IPV4`**: IPv4 primary stream established and served `GET /`; no IPv6 SYN sent.
- **`IPV6_TO_IPV4_FALLBACK`**: IPv6 SYN sent first; IPv4 SYN sent subsequently; IPv4 primary stream successfully served `GET /`.
- **`IPV4_TO_IPV6_FALLBACK`**: IPv4 SYN sent first; IPv6 SYN sent subsequently; IPv6 primary stream successfully served `GET /`.
- **`CONNECTION_FAILED`**: Neither address family established a primary HTTP connection.
- **`INCONCLUSIVE`**: Measurement anomaly, zero packets captured, capture interface drop $>0$, or uncorroborated telemetry.

### 7.2 Trial Validity Enum (`TrialValidity`)
- **`VALID_LIVE`**: Fully valid live trial executed inside network namespaces with non-zero packet capture and verified pre/post conditions.
- **`SIMULATION`**: Synthetic or simulated execution.
- **`CLEANUP_FAILURE`**: Preflight check or post-trial teardown failed, preventing trial validation.
- **`MEASUREMENT_FAILURE`**: Measurement hardware/driver failure or packet buffer overrun.
- **`CORRUPTED_RECORD`**: Missing essential fields, invalid JSON, or schema parsing failure.

## 8. Capture Vantage Point & Evidence Integrity (Amendment A4 & A13)

### 8.1 Vantage Point Specification (Amendment A4)
All packet-derived metrics are defined strictly at the **client-side capture vantage point**:
- **Namespace**: `ps028-cl` (Client)
- **Capture Interface**: `ps028-cl-rt` (veth interface connecting client to router)
- **Timestamp Clock**: Linux kernel packet reception epoch timestamps (`SO_TIMESTAMP` / `frame.time_epoch`).
- **Dissector Configuration**: TShark 4.2.2 with explicit flags `-o tcp.relative_sequence_numbers:FALSE`.

### 8.2 Provenance Sidecars (Amendment A13)
All derived data files (`attempts.csv`, `connection_attempts.csv`, `trial_timeline.csv`) contain pure experimental data and NEVER contain generation timestamps or environment ephemera that would break byte-identical reproducibility. Execution metadata is stored strictly in sibling JSON files: `<export_path>.provenance.json`.

## 9. Four Evidence Classes (Rule R6)

1. **Class A: Deterministic Unit Tests** (`lab/test_*.py`): Fully offline, mock-based tests verifying algorithms, state machines, and schemas.
2. **Class B: Synthetic & Fixture PCAP Tests** (`tests/`, `lab/test_analyze.py`): Boundary fixtures testing synthetic packet timestamps (<10ms, >2000ms, corrupt headers).
3. **Class C: Historical Authentic-PCAP Validation**: Offline re-derivation across all 280 preserved October 29 campaign PCAPs.
4. **Class D: New Live Acceptance**: New live network namespace executions performed ONLY under explicit operator approval.
