Abstract & Problem Description
Section 1 · Slide 2/11
The Dual-Stack Fallback Challenge
As the global Internet migrates toward IPv6-dominant networks, client operating systems and browsers operate in mixed dual-stack environments where IPv6 paths may experience silent blackholing, router drops, or severe latency degradation. Standard TCP connection timeouts (21–75 seconds) cause severe application stalls if IPv6 is naively serialized. Happy Eyeballs (RFC 8305) addresses this by racing address families.

Background & Testbed Foundations
Section 2 · Slide 3/11
Happy Eyeballs v2 (RFC 8305) Principles
  • IPv6 Preference (§2 / RFC 6724): Resolvers return both A and AAAA; host destination policy favors IPv6 for initial attempt.
  • Resolution Delay (§3): If A arrives before AAAA, client RECOMMENDED to wait 50 ms before launching IPv4.
  • Connection Attempt Delay (CAD, §5): If IPv6 attempt does not complete, subsequent IPv4 attempt starts after CAD timer (recommended default 250 ms, bounds 100–2000 ms).
  • Mandatory Floor (§5): Subsequent attempts MUST NOT start within 10 ms of previous attempt.
Network Namespace Isolation Architecture
  • Client NS (ps028-cl): Clean profile execution, unprivileged browser runners, isolated resolver.
  • Router NS (ps028-rt): Dedicated veth routing with Linux tc-netem shaping and nftables stateful dropping.
  • Server NS (ps028-sv): Independent IPv4/IPv6 dual-stack legs (ps028-rt-sv4 / ps028-rt-sv6) preventing cross-family impairment coupling.
  • Controlled DNS: Custom Python UDP DNS responder supporting nominal millisecond-valued per-family delay configuration. Effective delay accuracy and scheduling jitter were not independently calibrated to establish microsecond-level precision.

Proposed Experimental Architecture
Section 4 · Slide 5/11
Decoupled Dual-Leg Testbed Topology
Traditional dual-stack testbeds often share router-to-server links, causing IPv6 netem delays or loss to inadvertently corrupt IPv4 queues. PS-028 implements dedicated virtual interfaces:
• ps028-rt-sv4: Dedicated IPv4 transport (10.0.24.0/24)
• ps028-rt-sv6: Dedicated IPv6 transport (fd00:28:4::/64)
Zero cross-talk ensures completely independent impairment matrices.
Controlled Scenarios (S0–S6)
S0: Baseline dual-stack (10 ms RTT)  |  S1: IPv6 SYN blackhole (drop)
S2: IPv6 TCP RST rejection  |  S3: Symmetric delay (100 ms)
S4: Asymmetric delay (IPv6 600 ms, IPv4 10 ms)
S5: 50% IPv6 SYN loss  |  S6: Delayed AAAA DNS (500 ms)
Unprivileged Safety & Determinism
  • Zero Sudo Harness: Test runners execute as unprivileged users; narrow operations mediated by privileged_helper.py with strict regex and integer bound validation.
  • Fail-Closed DNS Reload: 5-stage verification (PID validation, config backup, SIGHUP delivery, log readback, active query probe) guarantees deterministic DNS state.
  • Cryptographic Artifact Trail: Every trial generates an isolated PCAP, JSON record, and SHA-256 digest tracked in an append-only manifest.

Primary Flow Correlation Loose port substring heuristics; ambiguous on multi-flow browsers. Strict Wireshark http.request_in frame linking; isolates primary GET / from post-navigation requests with 0 misattributions.
Connection Timing Metric SYN-to-SYN/ACK interval (connection_setup_time_ms); deviated >1ms in 144/280 trials. Strict RFC 9293 t_connect_ms (initial SYN to primary final ACK) and t_setup_total_ms (first target-host SYN across IPv4/IPv6 to primary final ACK); locks initial SYN.
DNS Query Correlation Combined raw query counts; conflated concurrent transactions. Pairing by dns.id + exact normalized QNAME + family transport; independent tracking of Type 65 HTTPS/SVCB queries.
